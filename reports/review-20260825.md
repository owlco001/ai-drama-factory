## P0 阻塞

### P0-1 L2记忆ID与context_refs不匹配 → 上游结果永远传不下去
- 位置：`src/core-engine/src/main/kotlin/com/agentteam/core/orchestrator/Orchestrator.kt:151`（refs=`mem_${taskId}_$nodeId`）vs `src/core-engine/src/main/kotlin/com/agentteam/core/memory/MemoryStore.kt:63`（实际memId=`mem_task_${++seq}_$nodeId`）、`BaseSubAgent.kt:51`
- 问题：BaseSubAgent 按 `memoryId == ref || roleOrKey == ref` 查找，ref 格式两边均对不上（roleOrKey 是裸 nodeId 如 `n1`）。检索结果无法进入分析/创作上下文，四节点流水线退化为各节点只见自己的指令——核心链路（PRD US3）功能性失效。
- 建议：统一由 MemoryStore 生成并返回 memoryId，Orchestrator 用返回值构造 context_refs；或在 BaseSubAgent 中按 `node_id` 后缀匹配。补一条跨节点上下文传递的集成测试。

### P0-2 file_read 目录前缀校验存在兄弟目录绕过
- 位置：`src/core-engine/src/main/kotlin/com/agentteam/core/tools/impl/BuiltinTools.kt:54`
- 问题：`f.canonicalPath.startsWith(File(baseDir).canonicalPath)` 无路径分隔符保护。baseDir=`/data/data/knowledge` 时，`/data/data/knowledge_secrets/x.txt` 同样通过校验；canonicalPath 已解决 `..` 与符号链接，但兄弟目录前缀攻击可直接越界读取任意同前缀目录。
- 建议：改为 `File(baseDir).canonicalFile.let { base -> f.canonicalFile.path == base.path || f.canonicalFile.parentFile?.canonicalPath == base.path }` 或 `startsWith(canonicalBasePath + File.separator)`（另允许等于 base 本身）。同时补测试用例：`../`、绝对路径出界、symlink 指向外部、`knowledge_x/` 兄弟目录。

## P1 重要

### P1-1 节点失败后未短路后继依赖节点
- 位置：`Orchestrator.kt:84-103`
- 架构§6.1要求「FAILED重试仍败则标FAILED并短路，所有后继SKIPPED」。现实现失败后继续顺序执行后续节点，仅依赖预算检查。且 `markSkippedFrom()`（176-178行）忽略 `fromNodeId` 参数、把全部节点置SKIPPED，逻辑未被正确使用。
- 建议：维护已完成集合，`node.dependsOn.any { it !in succeeded }` 则置SKIPPED跳过。

### P1-2 六层保险中三层未落实
- 位置：`Orchestrator.kt`
- ① `RunBudget.deadline`（30行）计算后从未检查；② `MAX_REPLY_DEPTH`（37行）无任何引用，reply链深检测缺失；③ DAG无环校验未执行——`TopologyValidator.validate()` 在全工程无调用点，planTask 产物不校验环/拓扑。防死循环保险实际只剩轮次/单Agent次数/超时/重试四层。
- 建议：分派前调用 TopologyValidator 并做拓扑排序验环；deadline 纳入 while 条件；reply链深计数落地。

### P1-3 协程取消与超时不干净：CancellationException被吞、推理不停止
- 位置：`BaseSubAgent.kt:71-80`、`InferenceEngine.kt:44-52`、`Orchestrator.kt:135-139`
- `catch (e: Exception)` 会吞掉 `CancellationException`，破坏结构化并发——withTimeoutOrNull 取消后 agent 返回伪FAILED而非传播取消。另外超时只取消协程，从不调用 `engine.stop()`，native 推理继续空转到120s外，与「用户熔断随时取消、当前token生成停止」矛盾。
- 建议：catch 中 `if (e is CancellationException) throw e`；dispatchWithRetry 超时/取消路径调用 engine.stop()。

### P1-4 消息总线丢消息风险与锁不一致
- 位置：`bus/MessageBus.kt:26-46`
- ① `tryEmit` 缓冲满(1024)时静默丢弃，注释称「兜底」但无任何兜底实现；② `send` 用 `@Synchronized`(this)，`history` 用 `synchronized(log)`，两把不同的锁，log 的读写无互斥，可能 ConcurrentModificationException；③ `handlers` 非线程安全且 `dispatchHandlers` 不在 send 内触发，注册的路由形同虚设（除非外部约定，未见调用方）。
- 建议：tryEmit 失败时记录告警或改用 `emit`（挂起）；统一锁对象；dispatchHandlers 由 send 内启动协程调用或删除该半成品接口。

### P1-5 内存消息日志无界增长
- 位置：`bus/MessageBus.kt:29,34`
- `log += msg` 无上限、无淘汰。长会话+FINAL_OUTPUT含全文，直接违背 PRD §5.1 内存约束（≤2.5GB 含模型，堆内日志不受控增长会促发LMK/OOM）。
- 建议：环形缓冲（如 ArrayDeque 上限1000条）或尽快接 SQLite message_log（§5表已定义）。

### P1-6 剪贴板内容无脱敏直入持久化链路
- 位置：`tools/impl/BuiltinTools.kt:35-41`、`Agents.kt:44,52-53`、`BaseSubAgent.kt:57-58`
- clipboard_read 结果经 ToolExecAgent 写入L2记忆并作为消息广播/入日志。剪贴板常含密码、验证码等敏感文本，虽决议Q2允许该工具，但缺少：调用前的用户确认弹窗占位（decisions.md要求v1.1加运行时授权——至少留接口）、结果落库的脱敏/短保留策略。
- 建议：MVP至少在工具描述与日志中标注敏感来源，并在app层预留授权钩子。

### P1-7 taskId 用毫秒时间戳，可碰撞且非UUIDv7
- 位置：`Orchestrator.kt:69`
- `"task_${System.currentTimeMillis()}"` 同毫秒两次输入即撞 task_id，导致L2记忆串任务。架构§4要求 msg_id 用 UUIDv7，task_id 也应唯一。
- 建议：复用 newUuidV7()。

## P2 建议

### P2-1 failMsg 从 payload.toString() 字符串截取 node_id
- `Orchestrator.kt:168`：序列化格式变化即失效。应先 cast JsonObject 再取字段。

### P2-2 计算器不支持一元负号、除零返回Infinity
- `BuiltinTools.kt:24-29`：atom() 遇 `-` 直接抛异常（而 ToolExecAgent 的正则会匹配到 `-(...)` 形式，见 Agents.kt:49，导致工具必失败）；`1/0` 得 Infinity 且 ok=true。建议 atom 支持 `-`，除零返回错误。

### P2-3 FileReadTool 默认 baseDir 硬编码非法路径
- `BuiltinTools.kt:44`：`/data/data/knowledge` 缺包名，Android上不可写不可读。应由app层注入 `context.filesDir/knowledge`。

### P2-4 TASK_PLAN payload 为空壳，违反§4.2 schema
- `Orchestrator.kt:183`：`{"nodes":[]}` 不满足 required nodes 数组元素定义。应序列化真实 DAG 或在文档标注豁免。

### P2-5 InMemoryMemoryStore 非线程安全 & trim O(n²)
- `MemoryStore.kt:32-58`：l1/l2/l3 无同步，若未来多协程访问有竞态；trimShortTerm 每次全表过滤求和。建议加 Mutex 或注明单协程约束。

### P2-6 VerifierAgent 失败结果也写入L3
- `Agents.kt:65-72`：status=FAILED 时 summary 是 error 文本，不应沉淀长期记忆。建议仅在 OK 时 upsert。

### P2-7 handleUserInput 未发送 USER_INPUT 消息、未写L1短期记忆
- `Orchestrator.kt:68-117`：USER_INPUT 类型枚举闲置，L1 appendShortTerm 无任何调用点，三层记忆实际只有L2/L3在工作。

### P2-8 测试覆盖缺口
- 已有测试覆盖基本调度/白名单/LRU，但缺：P0-1跨节点上下文传递、file_read穿越用例（含兄弟目录/symlink）、SharedFlow缓冲满行为、cancelCurrent在推理中途的真实中断。
